# Porting a Walkthrough to the Next.js Stack

Guidelines for taking a mature vanilla HTML/CSS/JS interactive from `numeracy-explainers/` (see its `GUIDELINES.md` and `APP-SHELL-LAYOUT.md`) and porting it to the Next.js 16 / React 19 / TypeScript / Tailwind 4 / shadcn stack this app (`addition-explainers/`) established. Treat `addition-explainers/` as the reference implementation — when in doubt about a pattern, read its code before inventing a new one.

## The golden rule: port, don't redesign

**A "move this to the new stack" request is a faithful port, not a rewrite-with-improvements.** This came up directly on the addition port: an unrequested simplification of the desktop chrome drew immediate pushback — *"Why did you change the layout? The task was to update the stack... right?"* Unless the user separately and explicitly asks for UX/layout/copy changes, the new-stack version should be behaviorally and visually indistinguishable from the vanilla original to someone using it. A framework rewrite makes it tempting to "clean things up" along the way — don't. Every layout decision, copy string, animation timing, and breakpoint value in the vanilla file is the product of many prior feedback rounds; treat it as a spec, not a rough draft.

Concretely: keep a tab on the vanilla `index.html` open (or re-`Read`/`Grep` it) for the entire porting session, and diff your React output against it repeatedly — not just once at the start. Several real mismatches in this project were only caught on a dedicated "cross-check every point against the html version" pass done *after* the initial port seemed complete (wrong CSS breakpoint, wrong component markup for the mode toggle and progress bar, a visual rebuilt as a flat square instead of vanilla's grid-of-units, narration copy that drifted). Budget for that pass — don't assume a first port is done just because it renders and no console errors.

## Scope discipline

Confirm scope before starting, ideally via `AskUserQuestion` if it's ambiguous:
- Which specific file(s) are in scope — not the whole `numeracy-explainers/` folder unless asked.
- Whether this is a new parallel app (the addition port's approach: a brand-new top-level folder, vanilla files untouched) or an in-place replacement.
- Any stack pieces mentioned that might be for unrelated future work (e.g. React Flow/dagre was mentioned once but was for a different, unrelated piece — confirmed via a clarifying question, not assumed).

## Architecture pattern

- **One config-driven component tree, not N near-duplicate ones**, when a series has multiple similar pieces (e.g. stage2/stage3 of the same concept). Diff the vanilla files first — if they differ only in data (`places` array length, validation ranges, whether carry ever triggers, copy strings), that's a config difference, not an architecture one. One `lib/<concept>/config.ts` with typed config objects per variant, one shared component tree, thin per-route page wrappers (`app/stage2/page.tsx` etc. each just instantiating the shared component with its config).
- **Pure logic layer first, no UI.** Port the vanilla's step/phase generation, validation, and narration logic into framework-agnostic TypeScript (`lib/<concept>/{types,config,phases,session,narration,visibility}.ts` in this app's layout) before writing any component. This is the highest-bug-risk part (carry propagation, phase indexing, MCQ generation) and is fully unit-testable without a browser. Write a standalone smoke-test script (this app's `npm run test:logic`, run via `tsx`) that exercises a full playthrough of every variant, including any carry/regroup path — and specifically regression-test any bug the vanilla version's own history recorded (e.g. this app's smoke test exercises the vanilla project's own documented "carryIn double-increments after Prev" bug via a `GO_BACK` action).
- **`useReducer` + a small local Context**, not a global store, when the state is single-owner per mounted instance. A module-singleton store (zustand, etc.) would leak state between routes/instances unless built as a factory — more ceremony than `useReducer` already gives for free. Only reach for a shared store if state genuinely needs to be shared across otherwise-unrelated components (the repo's `fair-share` app uses zustand for exactly that reason — cross-cutting sound/phase state across a flatter tree — which doesn't apply here).
- **Hand-roll single-purpose interactions instead of pulling in a generic library**, when the interaction genuinely has one drop target and one item type at a time (e.g. drag-a-block-into-a-total-cell). A collision-detection library like `@dnd-kit/core` earns its keep when there are multiple simultaneous drop targets or item types; it adds nothing here over a direct Pointer Events implementation ported straight from the vanilla's own (already-proven-through-many-iterations) logic. Don't default to "use the repo's established library" if the interaction doesn't need what that library provides — but do default to it when there's genuine ambiguity, since consistency has its own value.
- **Effects over imperative calls for "auto-advance" behavior.** If the vanilla version imperatively calls an advance function from inside a commit handler, prefer a `useEffect` keyed on the relevant session fields instead, firing on phase-mount regardless of whether any user action happens. This is a genuine improvement, not just a stylistic swap — it naturally fixes a class of bug where a target of zero (nothing to drag) never triggers the imperative call and the walkthrough gets stuck. If you make this kind of a "better than the original" call, do it because it's *more correct*, not because it's more idiomatic React — and don't extend that license to layout/copy/timing decisions, which stay locked to the vanilla spec per the golden rule above.

## Preserve exactly, port faithfully

These are **not** simplification targets, no matter how much cleaner an alternative looks in React:
- Stage/animation timing constants (durations, delays) — copy the literal millisecond values.
- Every text string, including narration copy, button labels, and error messages — no rewording, no "cleaning up" phrasing, unless the user asks.
- Exact CSS pixel values for anything visually load-bearing (font sizes at each breakpoint, component dimensions like a toggle's track/thumb size, spacing). When unsure of an exact value, go re-read the vanilla `<style>` block rather than eyeballing a screenshot.
- Any place the vanilla version uses raw, low-level DOM/CSS markup for a *specific reason* (e.g. a hand-drawn grid of tiny divs to represent 100 individual units, not a solid block with a texture) — rebuild that same structure in JSX, don't substitute a simpler-looking equivalent that only *reads* similar from a distance.
- Color semantics that reference a *different* element than the one being styled (e.g. an animation previewing a value's *destination* place should use that destination's color, not the source's, or a hardcoded accent color) — these are easy to flatten into "just use the theme accent color" by accident when re-deriving styles from scratch instead of porting the vanilla's actual logic.

## Simplify/replace, deliberately (with reasoning, not by default)

Some vanilla patterns exist specifically because vanilla JS lacks a component model — these have a strictly-better React-native equivalent and should be replaced, not ported literally:
- DOM-node-reparenting tricks for mobile-vs-desktop layout (e.g. moving the same options panel between a bottom sheet and a header depending on `matchMedia`) → plain conditional JSX rendering via a `useMediaQuery` hook. This eliminates an entire class of `matchMedia`-timing bugs the vanilla version needed workarounds for across many rounds.
- Hand-rolled custom dropdown/modal widgets that exist only because native `<select>`/no-JS-modal didn't meet a specific requirement → shadcn's `DropdownMenu`/`Sheet` (Radix-based), which get focus trapping, outside-click, Escape, and collision positioning for free for the same requirement.
- Manual SVG stroke-dasharray perimeter math for a draw-on animation → Framer Motion's `pathLength` animatable prop, same visual result, far less code.
- A hand-tuned pixel-width truncation ritual for a single always-static text value → plain CSS `text-overflow: ellipsis`, unless the field's content is genuinely dynamic/variable-length in a way that needs the calibration.

When deciding whether something belongs in this list or the "preserve exactly" list above: ask whether the vanilla pattern exists because of a *language/platform limitation* (belongs here) or because of *deliberate design/pedagogical intent* (preserve it exactly). When genuinely unsure which it is, preserve it — the cost of an unnecessary but harmless port is much lower than the cost of an unrequested design change.

## Animation

- For any "commit state, then measure/animate off the new DOM position" sequence (a common shape for pack/carry/regroup animations), prefer `flushSync` from `react-dom` over a `requestAnimationFrame`-based wait. A double-rAF wait for "let the re-render paint" is fragile in general and additionally **hangs indefinitely** in this project's own Browser-pane test harness (see Testing section below) — `flushSync` forces the state-committing re-render to apply synchronously, with no rAF/timer dependency at all, and is simpler and more correct for real users too, not just a testing accommodation.
- Prefer Framer Motion's declarative primitives (`animate`, `AnimatePresence`, `layoutId`/layout projection) for the parts of an animation sequence that are genuinely declarative (a glow loop, a draw-in stroke, a FLIP-style position transition), but keep hard sequencing/ordering constraints (e.g. "the destination cell must exist in the DOM before you can measure it") as explicit hand-rolled `async` orchestration — don't force a multi-stage choreographed animation into a single declarative expression just because the pieces individually could be declarative.
- If the vanilla version manually corrects a FLIP-style translate distance for an outer `scale()` transform (a scaled workspace container), check whether your chosen animation approach needs the same correction or handles it automatically. Framer's `layoutId`-based layout projection defers measurement to its own post-render step and computes the correct delta automatically even under a scaled ancestor — this is a genuine advantage over hand-rolled FLIP math, not just a stylistic preference, if you use it.

## Responsive breakpoints — verify the actual value, don't assume a default

This app's real desktop threshold is `900px` (matching the vanilla project's `DESKTOP_QUERY`), expressed as Tailwind arbitrary-breakpoint syntax `min-[900px]:...` throughout — **not** Tailwind's default `sm:` (640px) or `lg:` (1024px) breakpoints. A real bug shipped in an earlier round of this exact port: several components used `sm:` instead of `min-[900px]:`, so "desktop" styling silently activated at the wrong width and used the wrong pixel values even when it did trigger — this went unnoticed until a dedicated fidelity pass compared rendered sizes against the vanilla spec directly. When porting a piece with its own desktop/mobile split, grep the vanilla CSS for its actual media-query breakpoint value and use *that* value in every arbitrary-breakpoint Tailwind class — don't reach for a default Tailwind breakpoint name out of habit.

For the fit-to-viewport workspace pattern (vanilla's JS-measured `scrollWidth`/`scrollHeight`-vs-container scale-to-fit), port it as a small hook (`useFitWorkspace` in this app) driven by a `ResizeObserver` plus a dependency array of the session fields that change the rendered content's natural size — re-run the fit calculation on every one of those, not just on window resize.

## Testing and verification — harness-specific gotchas

These are lessons specific to this project's Browser-pane test harness, on top of the general ones in the `browser-verify-mfe` memory. All stem from one root cause: **the Browser pane doesn't composite frames when not actively displayed/focused**, which throttles or freezes anything that depends on a real paint cycle.

- **One discrete action (one click, one drag) per separate tool call.** Rapid synchronous loops dispatching multiple pointer events, or `async` loops with `setTimeout`/`sleep` between actions, either read stale DOM references (producing miscounted state) or hang on throttled timers until the tool's own timeout. This has held across every drag-heavy verification pass in this project — don't try to batch.
- **CSS transitions never progress in this harness** — `getComputedStyle`, `offsetWidth`, and `getBoundingClientRect()` on an element with an active `transition` report its pre-transition value indefinitely, even though the element's actual `style` attribute / target CSS values are correct from the very first render. Verify via the raw `style` attribute (`el.getAttribute('style')` or `el.style.<prop>`) instead of computed/measured values for anything that might be mid-transition.
- **This same freeze can silently break interaction testing, not just visual verification.** A collapsed-then-expanding wrapper's `getBoundingClientRect()` can report a stale zero-size box, which breaks `document.elementFromPoint(x, y)`-based drop-target hit-testing used by custom drag implementations — a synthetic drag dispatched at a drop target's nominal center can silently miss (hit-test falls through to a parent element instead) with zero console errors, looking exactly like a broken feature. Passing an explicit `target` to a synthetic `pointerup` dispatch does **not** fix this if the app's own handler independently calls `document.elementFromPoint(ev.clientX, ev.clientY)` internally — only an actual repaint fixes it.
- **The fix/diagnostic for a frozen pane: force one real compositor paint.** Calling `computer{action:"screenshot"}` once — even if the screenshot image itself isn't what you need — forces a real paint as a side effect and un-freezes subsequent `getBoundingClientRect()`/`elementFromPoint()` calls in that tab (until the next burst of rapid synthetic events re-freezes it). If a drag/interaction test inexplicably fails to commit with no JS error, try this before assuming a real bug.
- **Screenshots themselves can be unavailable** ("the Browser pane is not displayed, so the page is not compositing frames") depending on whether the pane is actually shown in the current session's UI. When that's the case, verify mobile/responsive layout via DOM inspection (`window.innerWidth`, `getBoundingClientRect()` on key elements, `getComputedStyle` for non-transitioning elements) rather than visual screenshots — confirm the real viewport width first (`window.innerWidth`/`innerHeight`), since `resize_window` has separately been unreliable about actually taking effect without a subsequent navigate/reload.
- Prefer tabs that have already had a real navigate + resize over freshly `tabs_create`d ones when investigating a rendering mystery — fresh tabs have intermittently come up with a `0×0` viewport that never recovers.

## Deploy

Static export via `output: 'export'` + `trailingSlash: true` in `next.config.ts` (so each route emits its own `index.html`, required for `here.now` to serve it correctly). Build with `next build`, verify the `out/` directory structure directly (each route's own folder with an `index.html` inside) before publishing — dev-server-only behavior can differ from the static export. Publish via `~/.agents/skills/here-now/scripts/publish.sh out`. A multi-route Next.js app publishes as a **single** `here.now` deployment serving all routes (landing page at `/`, each variant at its own path) — this is a genuine improvement over multiple vanilla files each getting their own independent `here.now` site, since same-origin relative links between variants (e.g. a "next stage" link) now actually work, where they'd 404 across two unrelated deploys.

The publish step can take long enough (dozens of files vs. a raw HTML folder's 1-2) to exceed a default synchronous command timeout — run it in the background and wait for the notification rather than assuming a short timeout means failure. Every publish creates a **fresh anonymous slug** (24h expiry) unless a prior claim state is present in `.herenow/state.json` for that exact folder — check that file for the current slug before handing a link to the user, and re-verify the live URL directly after every redeploy rather than trusting the publish log alone.

## Pre-"done" checklist

Before reporting a port as complete:
- [ ] Full playthrough of every config variant, including any carry/regroup/edge-case path (e.g. a target of zero), verified end to end — not just that it renders once.
- [ ] A dedicated fidelity pass: read through the vanilla source's structure/CSS/copy again, point by point, and diff against the port — don't rely on your first-pass memory of "what it should look like."
- [ ] Both mobile and desktop viewports checked with a *confirmed* real viewport size, console clean at both.
- [ ] `tsc --noEmit`, any logic smoke-test script, and `next build` all pass clean.
- [ ] `out/` structure spot-checked directly.
- [ ] Published and **re-verified against the live URL**, not just a "publish succeeded" log line.
